# rc2fx-native

`librc2fx_native.so` runs RC2FX's audio processing directly inside RØDE's stock `rc_audio_mixer` on qualified firmware profiles. RØDE's launcher invokes the RC2FX shim instead of the stock binary, and the shim runs `mixer/scripts/rc2fx.sh launch`, which execs the stock mixer with this library loaded via `LD_AUDIT`.

This is a Linux-only `cdylib` with its own Cargo workspace. `just mixer-build` cross-compiles it for the mixer.

## Hooks

Using the ELF audit interface, the library intercepts six `libjack` bindings made by the mixer:

- process callback registration,
- xrun callback registration,
- buffer lookup,
- client close,
- port registration,
- port unregistration.

Internal `libjack` calls and `dlsym` lookups are untouched. The xrun wrapper logs `jackd`'s notification before forwarding it to the mixer's own xrun callback.

The mixer's process callback is only wrapped at the executable-relative offset listed in `config/firmware-profiles.json`, and only after verifying both the executable hash and the original instructions at that offset. If either check fails, the stock callback runs unwrapped. The same verification gates a small fix for a vendor job in that callback that referenced stack locals after they went out of scope.

At startup, the library reads the launch plan generated by `rc2fxd plan`, binds every listed path, and runs `rc2fx-dsp` on the selected ones. The audio callback itself never locks, allocates, or blocks.

`rc2fxd` talks to the library over a Unix control socket (`rc2fx-native-control`) to push live settings changes (no mixer restart needed) and to pull meters and timing data.

## Outputs

Outputs (USB sends, headphones, and monitors) are processed in place during the audio callback, right after the mixer's own processing finishes and before the callback returns in the same frame.

## Sources

Sources are offloaded to a helper thread using copies handed over by the callback:

1. At the end of each callback, the callback copies the source frame into a private double buffer and signals the helper.
2. The helper processes it through `rc2fx-dsp`.
3. On the next callback, the mixer gets the processed buffer.

That adds one frame (2.3 ms) of latency to processed sources. The original source buffer stays untouched for any other mixer consumers, and the helper never touches buffers owned by `jackd`.

If the helper hasn't finished when the next callback arrives, the callback waits up to 200 µs. If it's still busy after that, the raw frame passes through once and the miss is recorded (`helper.late`, `helper.stalls`, plus `helperBusy` and `helperStall` events).

Unprocessed paths are left alone; their buffers are only looked up every eighth callback to read meters.

### Helper placement

The helper thread is pinned to whichever audio cores the callback isn't using, at one real-time priority below the callback. That keeps it out of the callback's way while giving it most of a period to finish each frame. Before RØDE pins the callback, or if the callback spans all audio cores, the helper still stays on the audio cores and off CPU 0, which is reserved for the suppression worker.

The callback checks its own placement every 64 callbacks until it's running real-time on its dedicated cores and the helper has applied the matching mask (for at most the first 8192 callbacks), then slows down to checking every 2048 callbacks. Because the helper only reads placement updates when starting a frame, changes are sampled at handoff. If a check lands on a callback where the helper is busy, it defers to the next handoff and increments `placement.deferred`.

Until the first placement update lands, the helper runs with its initial thread placement, so the earliest callbacks aren't covered. `placement.history` in the audit report keeps the first 16 placement changes after load without overwriting, logging the pipeline, callback mask/policy/priority, requested vs. actual helper placement, cycle number, deferral flag, and monotonic timestamp.

### Why the helper

On-device measurements with a microphone (noise suppression + EQ) and stereo headphone EQ enabled showed RØDE's own callback taking 670–750 µs, starting 300–600 µs into the 2333 µs period. Running ~240 µs of DSP inline pushed about 0.1% of callbacks past the deadline under USB audio load, turning each overrun into an xrun. Moving DSP to a helper on the same core as the callback left it preempted half the time, which led directly to the separate-core placement above.

## Noise suppression

DeepFilterNet3 noise suppression runs on its own worker from `rc2fx-suppression`, falling back to the delayed dry signal if a frame arrives late. Only one enabled target can hold the suppression slot at a time (either a mono microphone or the Chat voice mix), and it keeps that slot while bypassed or deselected.

### Chat

For Chat, `chat_mix` pulls only the microphone contributions from the qualified vendor routing functions, after per-source processing and fader gains across main, custom, solo, and mix-minus routing. Each original vendor function is still called once and vendor routing objects are treated as read-only.

Four hash-pinned detours installed before any threads start supply a stem for the current callback. If the layout doesn't match or a stem is missing, suppression is skipped on the completed mix. `rc2fx-dsp::Chat` runs a single mono model and voice gate, delays the stereo bypass to match, and then runs the standard stereo output chain. SMART Pads and playback bypass the model and voice gate completely.

Automated tests verify the detours against the vendor's ARM64 code using an emulated oracle and trampoline tests. Live sound quality with the trained model, simultaneous speakers, and whether the SMART Pad bypass is audible still need hands-on testing on hardware.

## Source accounting

The `sources` block in the audit report breaks down what the mixer actually received for every source frame that was supposed to be processed:

- `processed`,
- the first reason a raw buffer was returned:
  - `rawHelperUnready`,
  - `rawNoHandoff` (first frame, or the frame after a stall, inactive frame, or mode switch),
  - `rawNotDone`,
  - `rawInvalid`,
- `unobserved` (when the mixer never requested the buffer).

Any frame with a raw request is excluded from `processed`, and `rawReturns` counts the raw requests themselves. All counters are cumulative from library load (including startup), so diff two snapshots over a window. They don't tell you what the mixer does with a buffer after reading it, whether it reads it again after the callback, or the physical input-to-headphone latency.

## Environment

`rc2fx.sh` exports these variables:

| Variable | Meaning |
| --- | --- |
| `RC2FX_FIRMWARE_PROFILES` | Path to the validated firmware catalog (falls back to the embedded catalog) |
| `RC2FX_FIRMWARE_PROFILE` | Expected profile ID; exact executable hash selects and verifies it |
| `RC2FX_NATIVE_PROBE_PLAN` | Launch plan JSON (version 1, 48 kHz, 112 frames, up to 32 paths, 64 KiB max) |
| `RC2FX_NATIVE_PROBE_CONTROL_SOCKET` | Control socket path for `rc2fxd` |
| `RC2FX_NATIVE_PROBE_REPORT` | Audit report path, rewritten every second with callback, helper, and jackd-cycle timing, xruns, and recent anomaly events |
| `RC2FX_NATIVE_PROBE_EVENTS` | Append-only log updated once a second with timestamped anomalies (late callback starts/ends, helper late/stalled, gaps, xruns, late vendor jobs, USB gadget rebuilds), each tagged with time since the last USB control report |
| `RC2FX_NATIVE_PROBE_REPORT_SELECTED_ONLY` | Set to `1` to report processed paths only |

## Reading xrun diagnostics

`xruns` counts notifications delivered to instrumented JACK clients (not unique failed periods or confirmed audible dropouts), and the client receiving the notification isn't always the one that ran late.

In an `xrun` event, both the legacy `valueNs` and `notificationCyclePositionNs` report where the notified client was in its cycle when the notification arrived, not an overrun duration (or `null` if the clock wasn't available).

`lateEnd` events trigger at 90% of the period, while `cycle.lateEnds` counts estimated ends past the full period. Neither is a substitute for server-side logs.

The [JACK error recorder](jackerr/README.md) is loaded into `jackd` on every RC2FX start and logs the late client and state (or ALSA error) directly from the server. Run `just mixer-xruns` to inspect a window, and cross-check it with callback, helper, and worker diagnostics before touching buffer sizes.
