## Old repository findings that constrain the next experiment

The old checkout's `tools/diagnostics/usb-out-map.md` establishes that USB
callbacks perform ALSA availability/write calls and linear resampling. USB
threads set themselves to RR50 on CPUs 1–3. It explicitly warns that USB span
uprobes caused scheduling-while-atomic faults on the device's RT kernel; do not
reuse that measurement technique here.

`research_notes/argon-zero-xruns-2026-11-01.md` (available through the old
repository's Git HEAD) retracts earlier harmless-xrun claims. Its Pool affinity
experiment did not reduce notifications and worsened some helper/callback

## Remaining discriminating measurement

Ranked possibilities, still unproven:

1. USB callback starts too late in the graph despite a short execution time.
   Measure its entry/exit cycle positions alongside the main callback.
2. Occasional USB callback execution or ALSA blocking consumes the remaining
   period. Measure individual wall time and sampled thread CPU, preserving
   failure-adjacent records rather than just lifetime maxima.
3. Runnable scheduling interference delays an otherwise timely USB callback.
   Correlate per-callback timing with scheduling evidence; aggregate schedstat
   is insufficient.

The current native `set_process` hook deliberately forwards non-main callbacks
unchanged. A USB timing probe must preserve that lifecycle behavior: original
arguments and return values, failed registrations, null callbacks, successful
close quiescence, client-pointer reuse, and bounded slot exhaustion. Require
host tests at the registration/callback/close seam before any deployment. Use
fixed storage and no callback allocation or formatting; distinguish unavailable
clocks from zero duration, and report probe overhead. Do not route USB callbacks
through the main DSP pipeline merely to obtain timing.

## Optional callback probe implementation

`client_timing.rs` wraps non-main process callbacks only when the launcher sees
`/run/rc2fx-client-timing` at mixer startup. The launcher sets the environment
flag explicitly to zero otherwise. The marker is RAM-only; removing it disables
the probe at the next start. Do not create it or restart audio without agreeing
on the measurement window with the user.

`audit.json.clientTiming` identifies registrations by immutable slot index,
client address, callback address, JACK client name (when available), and observed TID. These are registration
lifetimes, including failed/replaced/closed registrations, not a live-client
inventory. Slots are never reused; after 128 registrations the probe forwards
unchanged and increments `exhausted`. If a JACK client name is unavailable, callback addresses require mapping to
the current vendor executable before naming a USB client. TIDs likewise require
current process identity verification.

Each registration has aggregate wall and sampled CPU timing plus the newest 32
locally late callback records. Records preserve entry/exit monotonic timestamps,
an estimated cycle start and a 48 kHz frame-derived budget. Cycle position is an
estimate, not JACK's own deadline check. Unknown cycle clocks remain null.
`outsideWindow`, `dropped` and `unavailableInWindow` expose history limitations.
The history uses atomic publication and rejects changing rows; writers do not
wait on readers. Aggregate CPU timing is sampled, not per-incident CPU time.

Tests cover argument/result forwarding, failed and null native registration
results, retained old callback arguments, client address reuse, slot exhaustion,
late entry versus long execution, history wrap and concurrent snapshot coherence.
A release-mode host benchmark is available as the ignored
`client_timing::tests::callback_probe_overhead` test. Its no-op vendor callback
and unavailable JACK clock do not predict actual ARM/device overhead.

to collect evidence or a sufficient normal-use acceptance test.
